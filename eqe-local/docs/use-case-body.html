Summary

The EQE dashboard turns requirements in Jira into an evidence-backed release decision for the StayEase hotel booking application. Seven stages run in the background: six AI agents and one human approval gate. The automation lead watches each stage, reviews the designed test cases, and reads the resulting QE lead report, traceability and defects.

Primary actor
Automation lead / EQE lead (reviewer and sign-off owner)
Goal
Know whether a StayEase release meets the agreed release criteria, with traceability from every acceptance criterion to a real test result.
Trigger
The lead starts a cycle on the dashboard Run page.
Preconditions
Mock Jira holds an initiative (MGPP-1) with epics and stories (EQE-2 to EQE-10) carrying acceptance criteria; the selected StayEase release is running.
Success outcome
A completed cycle with test cases, Playwright scripts, real results, Jira bugs for failures, traceability and a Go / Conditional / No-go decision.
Constraint
Everything runs locally. Nothing is pushed or deployed; no real client data or Jira is used.

How the agents reason. The agents are deterministic and rule-based. They apply the skills below, plus a real browser through Playwright MCP. They don't call a large language model, so the same requirements and release always produce the same test cases and results.

AI model by stage

No large language model (LLM) or other machine-learning model is used at any stage today. Each stage runs on deterministic rules and tools.

Main flow

01

Start a cycle

Lead

On the Run page the lead confirms Flow 1 (new baseline), picks the Jira initiative MGPP-1 and the StayEase release (1.0 or 1.1), enters the reviewer name, and chooses options: skip review, raise defects in Jira, slow-motion execution.

02

Read and analyse requirements

Agents 1–2

The requirements agent reads 6 stories and 17 acceptance criteria. The analysis agent finds 15 automatable, 1 ambiguous ("results load quickly") and 1 not UI-observable (confirmation email) criteria.

03

Design test cases

Agent 3

The test design agent produces the end-to-end journey (search Paris, view hotel, reserve, confirm, find reservation) and independent negative and variant cases, plus manual cases for criteria that can't be automated.

04

Lead review

Human gate

The cycle waits until the reviewer approves (optionally excluding cases). Nothing is automated before approval.

05

Generate scripts through MCP

Agent 5

The automation agent explores StayEase black-box through Playwright MCP (about 290–310 tool calls) and writes 13 Playwright specs with 7 page objects and 20 locators. Expected results not seen during exploration are flagged as possible defects.

06

Execute

Agent 6

The execution agent runs the specs headless. The lead can watch live frames from each browser; every test is recorded (video and trace).

07

Report and decide

Agent 7

The reporting agent raises Jira bugs for failures, builds traceability and applies the release criteria. The lead reads the QE lead report and signs off.

Skills and rules

EQE keeps its skills as versioned code and JSON in the local workspace. Changing them changes agent behaviour without touching the pipeline.

Scope and limitations

  • Flow 1 (new baseline) only. The DQE incremental flow (Flow 2), its Jira-vs-code gap check and its Test Lab are not part of EQE.
  • Jira is a local mock with the REST API v3 subset the agents need. Pointing JIRA_URL at a real Jira Cloud site would need authentication, which isn't built.
  • The application is tested only through the browser (black box). Code and APIs are not inputs.
  • Agents are rule-based, without a language model, so new kinds of acceptance criteria need a new technique in the skill catalogue.
